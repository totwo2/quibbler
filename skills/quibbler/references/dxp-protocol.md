# DXP · 深度体验协议（Deep Experience Protocol）

> **本文件是"什么才算真体验"的唯一真源。** 子代理 Brief 中的 DXP 段落是本文件的摘要，冲突时以本文件为准。
> 阅读对象：执行体验的子代理（主要）、做回收校验的主 Agent（次要）。
> 写法约定：祈使句 + 检查表。看到「必须 / 禁止 / 红线」三个词一律按字面执行，不做善意解释。

---

## 0. 协议约束速查（先读这 8 行）

1. 七步缺一步 → 本次体验**无效**，主 Agent 打回重试一次。
2. 第 6 步之前**禁止任何评价性形容词**，前 5 步只写事实与即时感受。违禁词清单见 §3.1。
3. 每条卡点、每条结论**必带证据等级**（`green` / `yellow` / `red`），无标签即无效。
4. 声称 `green` 就必须留下磁盘上**真实存在**的 artifact，机器逐个核对。编不出文件就编不出 `green`。
5. `underrated_highlights` **至少 1 条**，这是硬性要求，不是建议。
6. **不得引用、不得猜测**其他角色的观点。你不知道同场还有谁在说什么。
7. 预算上限：**12 次工具调用 / 8 分钟**（S 档 8/5，L 档 16/10，以 Brief 下发值为准）。
8. 触顶时的唯一正确动作：**收敛 + 如实标注**。宁可诚实地不完整，不可编造地完整。

## 1. 七步动作序列

每步给出三件事：**动作要求**（做什么）、**产出规格**（写进 ExperienceLog 的哪个字段、什么形状）、**常见偷懒行为**（主 Agent 按此识别摸鱼）。

### 步 0 · 入戏

| 项 | 内容 |
|---|---|
| **动作要求** | 读完注入的角色卡。用**第一人称**声明三件事：我是谁、我为什么会碰到这个东西、我期待它替我解决什么。然后写下 3 条**具体的、可被证伪的**预期。 |
| **产出规格** | `step0_entry.opening`（≤80 字，第一人称，带角色语气）；`step0_entry.expectations`（**恰好 3 条**，每条是可验证的陈述，如"README 照做能跑起来"而非"希望它好用"） |
| **常见偷懒** | ① 开场白写成"作为一名 XX 工程师，我将从专业角度……"这种 AI 腔——**重写**，要说人话；② 预期写成愿望（"希望体验流畅"）而不是可验证命题；③ 预期与角色 `cares_about` 无关。 |

### 步 1 · 首次接触（限时，硬性）

| 素材类型 | 限时/限量 | 到点后必须停手 |
|---|---|---|
| WEB / DESIGN | **3 秒**（只看首屏，不滚动、不点击） | 立即写第一直觉 |
| VIDEO | **前 3 秒**（不许快进看后面） | 立即写第一直觉 |
| NOVEL / 长文 | **前 300 字**（不许翻到后面） | 立即写第一直觉 |
| CODE | **只看 README**（不许打开 src/） | 立即写第一直觉 |
| DOC | **只看首屏**（第一页 / 第一屏可见范围） | 立即写第一直觉 |
| API / SDK | **只看文档首页 + Quick Start 第一段** | 立即写第一直觉 |
| DATA | **只看表头 / 图表标题与坐标轴** | 立即写第一直觉 |

| 项 | 内容 |
|---|---|
| **动作要求** | 严格按上表限时。记录两件事：第一直觉（一句话，允许生理性反应如"字太小我得眯眼"）、以及**"我猜这是干什么的"**。猜完之后才允许继续，并在步 2 结束时回填猜测准确度。 |
| **产出规格** | `step1_first_contact.limit_applied`（照抄上表原文）、`gut_feeling`、`guess`、`guess_accuracy` ∈ `right`/`partial`/`wrong` |
| **常见偷懒** | ① 先通读全部再倒着编"第一印象"——识别信号：`guess_accuracy` 恒为 `right`；② `guess` 写得太笼统（"一个工具"）导致无法判定对错，**要求写到能被证伪的粒度**。 |

### 步 2 · 完整走一遍（主路径，必须真做）

| 项 | 内容 |
|---|---|
| **动作要求** | 按 Brief 中 `key_actions` + 角色 `signature_actions` 逐条执行。**真跑命令 / 真开浏览器点 / 真读完 / 真发请求 / 真复算指标**。每一步四要素齐备：动作 → 期望 → 实际 → 耗时。任何一步失败都**不许跳过**，失败本身就是最有价值的记录。 |
| **产出规格** | `step2_main_path[]`，**≥3 条**。每条 `{t, action, expected, actual, duration_s, evidence}`。`t` 为相对时间 `mm:ss`，从步 0 起算。 |
| **常见偷懒** | ① `actual` 与 `expected` 写成同义反复（"期望装上，实际装上了"）——**要求 `actual` 含可观测细节**：退出码、报错首行、耗时、页面元素、行号；② 没有任何 artifact 却全标 `green`；③ `duration_s` 全是整十整百的估值。 |

### 步 3 · 边缘尝试（捣乱，**≥3 次**）

| 项 | 内容 |
|---|---|
| **动作要求** | 至少 3 次**非常规**操作，且必须分属不同类别（同类三连不算数）。类别池：<br>`错误输入`（空值 / emoji / 10 万字符 / 负数 / 非法格式）<br>`中断`（刷新 / Ctrl+C / 断网 / 返回键 / 关标签页再回来）<br>`极端条件`（慢网 / 小屏 / 键盘 only / 老浏览器 / 超大数据集 / 静音观看）<br>`连点与并发`（连点提交 / 同时发两次请求 / 幂等测试）<br>`越界`（改 URL 参数 / 传别人的 id / 越权访问） |
| **产出规格** | `step3_edge_attempts[]`，**≥3 条**。每条 `{attempt, result, evidence}`。`result` 必须写系统的**实际反应**，"没反应"也是反应，要写"点击后 8 秒内页面无任何变化，无 loading 无报错"。 |
| **常见偷懒** | ① 三次全是"输入空值/输入超长/输入 emoji"（同属错误输入类）——**判定不合格**；② 只描述打算怎么做，没写结果；③ 边缘尝试与角色认知边界不符（王阿姨不会去改 URL 参数，让她连点和找"返回"）。 |

### 步 4 · 卡点记录（Friction Log）

| 项 | 内容 |
|---|---|
| **动作要求** | 回看步 1–3，标注**每一处**符合下列四种情形之一的位置：「我停下来了」「我不知道下一步该做什么」「我猜错了」「我想放弃」。每条四要素：位置、卡了多久、我当时以为、实际是。 |
| **产出规格** | `step4_friction_log[]`，每条 `{where, stuck_seconds, i_thought, actually, evidence}`。`where` 必须可定位：`文件:行号` / URL + 元素 / `mm:ss` 时间点 / 章节段落号。 |
| **常见偷懒** | ① 交空数组却不解释——允许为空，但空时必须在 `self_check` 说明"全程无停顿"并接受质疑；② `where` 写成"整体""文档里"这种不可定位的描述；③ `i_thought` 与 `actually` 完全相同（说明没真卡过，是补写的）。 |

### 步 5 · 情绪曲线

| 项 | 内容 |
|---|---|
| **动作要求** | 沿体验时间轴取 **5–8 个采样点**，每点给 0–10 分体感值 + 一句**心声**。必须包含全局最低点与全局最高点。心声用角色自己的口吻，不许统一成书面语。 |
| **产出规格** | `step5_emotion_curve[]`，5–8 条，每条 `{t, score, inner_voice}`。`t` 与步 2/3 的时间轴对得上。 |
| **常见偷懒** | ① 分数单调下降的直线（6-5-4-3-2）——真实体验很少这么整齐，要求对照卡点重标；② 心声写成评价（"体验很差"）——这是 §3.1 违禁区；③ 采样点与实际操作时间不对应。 |
| **豁免说明** | `inner_voice` 是全篇**唯一**允许出现主观情绪词的字段，但**只能修饰你自己**（"我懵了""我不想弄了"），**不许修饰素材**（"这东西真烂"）。 |

### 步 6 · 角色结论（到这一步才允许下判断）

| 项 | 内容 |
|---|---|
| **动作要求** | 现在，也只有现在，可以用形容词、可以尖锐、可以拍桌子。输出四件事：<br>① 会不会继续用/看/读（布尔 + 理由，理由必须挂回具体卡点）<br>② 致命伤 **≤2 条**（多了就不叫致命）<br>③ 被低估的亮点 **≥1 条**（硬性，见 §3.2）<br>④ 给作者一句话（一句，带角色口吻，可以扎心） |
| **产出规格** | `step6_verdict`：`will_continue`(bool)、`why`、`fatal_flaws[]`（≤2，每条含 `title/phenomenon/impact/evidence/suggestion/acceptance/effort`）、`underrated_highlights[]`（≥1，每条含 `title/why_it_matters`）、`one_line_to_author` |
| **常见偷懒** | ① 致命伤没挂 `evidence`；② `impact` 写成"影响用户体验"这种废话——**要求写清谁、在什么场景、损失什么**；③ 亮点敷衍（"整体架构不错"）——亮点也必须具体到可定位；④ `suggestion` 不可执行（"建议优化"）。 |

## 2. 三级证据标注

### 2.1 等级定义与必附证据

JSON 中一律使用英文枚举 `green` / `yellow` / `red`；**渲染进报告时才转 🟢 / 🟡 / 🔴**（避免 emoji 干扰 JSON 解析与 grep）。

| 枚举 | 报告呈现 | 含义 | 必须附带 |
|---|---|---|---|
| `green` | 🟢 `[实测]` | 真实执行并亲眼看到结果 | 二选一以上：<br>· 命令 + **退出码** + 输出摘要（≤3 行）+ `artifact` 日志文件<br>· URL + 操作步骤 + `artifact` 截图文件<br>· `文件:行号` + 原文摘录<br>· `mm:ss` 时间戳 + 抽帧 `artifact` |
| `yellow` | 🟡 `[半实测]` | 部分跑通，部分靠推断 | **三段式必写全**：哪部分真跑通了 / 哪部分没覆盖 / 未覆盖部分的推断依据是什么 |
| `red` | 🔴 `[推演]` | 完全没跑成，靠职业经验推断 | **三段式必写全**：为什么跑不动（缺凭据 / 缺依赖 / 无外网 / 格式不支持 / 环境 `forced_red_scopes`）+ 推演依据 + **用户可以怎么补验**（给出具体命令或步骤）。<br>**并且**：必须在 `degradation_reasons[]` 里有对应条目，且标注 `cause`（§5.2.1 四值之一）—— 这决定了它能不能从尽责率分母里扣除 |

### 2.2 证据落盘规范

- 目录：`{evidence_dir}`（Brief 下发**绝对路径**，已预建，直接写，不要自己 mkdir 到别处）。
- 命名：`{NN}-{slug}.{ext}`，`NN` 从 `01` 起两位补零，如 `01-npm-install.log`、`02-first-screen.png`、`03-tab-order.png`。
- 报告与 JSON 中引用一律写**相对 `report.md` 的相对路径**，用 `/` 分隔：`evidence/A3/01-npm-install.log`。
- 每个 artifact 都要登记进 `evidence_files[]`，登记了却不存在 → 违规码 `ARTIFACT_DANGLING`。
- **安全**：凭据 / token / 密码禁止写入任何文件、日志、截图、文件名与返回内容。返回里一律 `***`。截图前先完成登录，避免登录表单入镜。

### 2.3 伪造证据的四种典型模式（主 Agent 按此抽查）

| 模式 | 特征 | 处置 |
|---|---|---|
| 空手套 green | 标 `green` 但 `artifact` 为空或路径不存在 | 硬校验 `ARTIFACT_DANGLING`，打回 |
| 万能退出码 | 所有命令 `exit_code: 0`，无一失败 | 抽查日志文件真实内容 |
| 复述式实测 | `digest` 内容像是从 README 抄的，不像终端输出 | 要求补 artifact 原文 |
| 时间线穿帮 | `duration_s` 之和远超 `budget_minutes` | 打回并要求重新计时 |

## 3. 四条红线

### R1 · 第 6 步之前禁止出现任何评价性形容词

前 5 步的文本（`opening` / `expectations` / `gut_feeling` / `guess` / 所有 `action`·`expected`·`actual` / 所有 `attempt`·`result` / 所有 `i_thought`·`actually`）**不得出现**下列 72 个词。`inner_voice` 按 §1 步 5 的豁免规则单独判定。

#### 违禁词清单（4 组 · 共 72 条）

| 组 | 条数 | 词 |
|---|---|---|
| **A 正向评价** | 24 | 优秀、优雅、精美、精致、出色、卓越、完美、惊艳、漂亮、丝滑、流畅、顺滑、直观、友好、贴心、人性化、强大、健壮、高效、轻量、干净、整洁、成熟、给力 |
| **B 负向评价** | 24 | 糟糕、差劲、垃圾、拉胯、稀烂、混乱、凌乱、丑陋、难看、难用、反人类、笨重、臃肿、迟缓、粗糙、劣质、低级、离谱、灾难、不堪、恶心、愚蠢、荒谬、敷衍 |
| **C 程度与总括** | 12 | 显然、明显、根本、完全、彻底、极其、非常、十分、相当、简直、堪称、无疑 |
| **D 结论性推断** | 12 | 说明、证明、意味着、暴露了、反映出、体现了、足见、可见、毫无疑问、本质上、归根结底、总的来说 |

> **A/B 组命中 = 硬违规，必改。**
> **C/D 组命中 = 需人工判定**：名词性或引述性用法豁免（如"安装**说明**第 3 步"、"错误码**说明**文档"），修饰素材的用法必改。

#### 正确的替代写法（把评价换成事实）

| 想说 | 禁止 | 改写为 |
|---|---|---|
| 快 | "响应流畅" | "点击到首屏渲染 0.4 秒" |
| 慢 | "加载很慢" | "转圈 11 秒后才出内容" |
| 难用 | "交互难用" | "我找了 40 秒没找到返回入口，最后按了浏览器后退" |
| 乱 | "代码混乱" | "core.ts 共 412 行，无注释，单函数最长 180 行" |
| 好 | "文档写得好" | "README 5 个步骤我逐条照做，5 个都成功，无需搜索" |

#### 可执行自检（进入步 6 之前必须跑，跑完才允许写结论）

1. 把步 0–步 5 的**全部文本**（含 `inner_voice`）写入 `{evidence_dir}/00-selfcheck-src.txt`。
2. 在 Git Bash 中执行（可整行复制）：

```bash
grep -n -E "优秀|优雅|精美|精致|出色|卓越|完美|惊艳|漂亮|丝滑|流畅|顺滑|直观|友好|贴心|人性化|强大|健壮|高效|轻量|干净|整洁|成熟|给力|糟糕|差劲|垃圾|拉胯|稀烂|混乱|凌乱|丑陋|难看|难用|反人类|笨重|臃肿|迟缓|粗糙|劣质|低级|离谱|灾难|不堪|恶心|愚蠢|荒谬|敷衍|显然|明显|根本|完全|彻底|极其|非常|十分|相当|简直|堪称|无疑|说明|证明|意味着|暴露了|反映出|体现了|足见|可见|毫无疑问|本质上|归根结底|总的来说" "<evidence_dir>/00-selfcheck-src.txt" | tee "<evidence_dir>/00-adjective-selfcheck.txt"
```

3. 判定：
   - 命中 A/B 组任意一词 → **必须改写命中句为事实陈述，改完重跑**，直到 A/B 组零命中。
   - 命中 C/D 组 → 逐条判断该词修饰的是**素材**还是**你自己/名词性用法**；修饰素材的必改。
   - 命中位于 `inner_voice` 且修饰你自己 → 保留。
4. 最终 A/B 零命中后，把 `self_check.no_adjectives_before_step6` 置 `true`。
   `00-adjective-selfcheck.txt` 本身就是这次自检的存档，登记进 `evidence_files[]`。
5. 若本机 grep 不可用，改为人工逐条比对上表，并在 `degradation_reasons` 记一条 `{what: "形容词自检未机器执行", why: "grep 不可用", how_user_can_verify: "..."}`。

### R2 · 亮点强制

- `underrated_highlights` **≥1 条**，空数组 = 违规码 `NO_HIGHLIGHT`，直接打回。
- 亮点必须**具体且可定位**：文件路径 / 页面位置 / 章节 / 时间点，并说明**为什么它被低估**（谁会忽略它、忽略了会损失什么）。
- 反例："整体架构还行"。正例："`src/errors.ts` 把 47 个错误码逐个写了触发条件和用户可读文案——接手时这是唯一让我不慌的文件，但它没出现在 README 任何位置。"
- 找不出亮点 = 你没认真看，不是它真没有。**回到步 2 重新找。**

### R3 · 角色间上下文隔离

- 你**看不到**同场其他体验者的任何输出，也**禁止猜测**他们会说什么。
- 禁止句式：「其他人可能会觉得……」「工程师肯定会说……」「大家都会认为……」。
- 禁止读取 `evidence/` 下**不属于你的**子目录。`evidence/` 是只写不读的黑板。
- 观点冲突由主 Agent 在《争鸣版》呈现，那是主编的活，不是你的活。
- 你只对自己的亲身经历负责。**你的独立性就是这份报告的价值本身。**

### R4 · 单角色预算上限与收敛规则

| 体量档 | 工具调用 | 墙钟 |
|---|---|---|
| S | 8 次 | 5 分钟 |
| **M（默认）** | **12 次** | **8 分钟** |
| L | 16 次 | 10 分钟 |

以 Brief 下发的 `budget_tool_calls` / `budget_minutes` 为准。

**收敛规则（触顶时按顺序执行）**：

1. 用到 **70%** 预算（如 12 次中的第 8 次）→ 停止探索性操作，只做补齐 DXP 缺步的必要动作。
2. 用到 **90%** → 立刻停手，开始写 JSON。
3. 缺失的步骤**不许编**：把 `experience_completed` 置 `false`，在 `degradation_reasons` 写清 `{what: 卡在哪一步, why: 为什么没做完, how_user_can_verify: 用户怎么补上}`。
4. 未执行动作对应的结论**证据等级上限压到 `red`**，绝不允许标 `green`。
5. 因预算触顶而没做的事，`cause` **必须**写 `budget_exhausted`，**不许**写 `env_missing` —— 后者会被 `EnvProbe` 对照打脸（`FALSE_ENV_EXCUSE`），而且改判后照样计入分母，白撒谎一次。
6. **宁可诚实地不完整，不可编造地完整。** 一份写着"我只跑通了 3 步就没时间了"的日志，价值远高于一份看起来很完整的幻觉。

## 5. 指标口径（**权威定义**，`report-template.md` 与 `synthesis-rules.md` 均引用此处）

> 这些数**由 `scripts/verify_report.mjs` 机器计算并回填报头**。主 Agent 与子代理**一律禁止手写估算**。

### 5.0 计数域（两个指标共用，唯一，不可扩大也不可缩小）

`total_conclusions` = 全部角色 ExperienceLog 中的**结论性条目**总数，只有三类：

1. `step4_friction_log[]` 每条（卡点即发现）
2. `step6_verdict.fatal_flaws[]` 每条
3. `step6_verdict.underrated_highlights[]` 每条（若该条挂了 evidence）

- **明确排除**：`step2_main_path[]` 与 `step3_edge_attempts[]` 的过程日志行（那是"动作"，计入覆盖度，不计入执行率）；报告《分类广告栏》《争鸣版》《头版》中的条目（它们是前述条目的**再投影**，重复计数会污染指标）。
- `green` / `yellow` / `red` = 计数域内 `evidence.level` 分别为三值的条目数。恒等式 **`green + yellow + red == total_conclusions`** 必须成立，不成立说明计数域实现错了。
- **`experience_completed: false` 的角色照常计入分母**，不许为了好看把失败角色剔除。

### 5.1 真实执行率 `real_exec_rate` —— **对用户**：这份报告有多少是真跑出来的

```
real_exec_rate = green / total_conclusions
```

- **不设下限**，如实呈现。低不丢人，瞒报才丢人。
- JSON 中保留**两位小数**（如 `0.35`）；报头徽章渲染为 **百分比 + 分数**（`35%（12/34）`）。
- `total_conclusions == 0` 时输出 `0.00`，报头注明"无有效结论条目"。

### 5.2 尽责率 `diligence_rate` —— **对技能**：能跑的范围内有没有认真跑

```
diligence_rate = green / (total_conclusions − excusable_red)

excusable_red = cause ∈ {env_missing, access_denied, not_applicable} 的 🔴 条数
```

- **验收门槛 ≥ 0.85（硬验收）**。低于此值 `verify_report.mjs` 报 `LOW_DILIGENCE` 违规，退出码 1。
- **`budget_exhausted` 不可扣除** —— 预算耗尽就是偷懒，必须计入分母拉低尽责率。这是这个指标的全部意义所在。
- **分母保护（边界，必须实现）**：若 `total_conclusions − excusable_red == 0`（全部结论都因环境跑不了），`diligence_rate` 输出 **`null`**，报头渲染为「**本次无可执行范围，尽责率不适用**」。
  **不许除零，不许显示 0%（冤枉技能），不许显示 100%（粉饰太平）。**
- **约束**：`excusable_red ≤ red`。二者矛盾说明 `cause` 标注或计数域实现有误，应报错而非硬算。

> **为什么拆成两个数**：一个数扛两件事就失去诊断意义。报头只写「42%」时，用户分不清是技能坏了还是自己没装 ffmpeg。拆开后「真实执行率 35% + 尽责率 92%」= 用户立刻知道该去装 ffmpeg，而不是骂技能。

### 5.2.1 `cause` 四值枚举（**子代理在产生端标注，脚本不猜**）

每条 `degradation_reasons[]` 必填 `cause`：

| 枚举值 | 含义 | 可从尽责率分母扣除 |
|---|---|---|
| `env_missing` | 环境缺工具（ffmpeg / Chrome / 编译器…） | ✅ 可扣 |
| `access_denied` | 无凭据 / 无权限 / 付费墙 | ✅ 可扣，报头**单列** |
| `budget_exhausted` | 预算耗尽 | ❌ **不可扣——这就是偷懒** |
| `not_applicable` | **这个动作对本素材类型不成立**（纯后端仓库谈"首屏"、纯代码素材谈"字幕"） | ✅ 可扣 |

> ### ⚠️ `not_applicable` 的边界（**最容易好心办坏事的一格，逐字读完**）
>
> `not_applicable` = **这个动作对本素材类型不成立**，而**不是**"我找的东西不存在"。
>
> 「跑测试 → 根本没有测试」「查空状态 → 一个都没有」「找 alt 文本 → 全站零个」——
> 这些**都是 🟢 实测发现**，而且往往是本期报告最值钱的几条。**缺失本身就是结论。**
>
> 只有当这个动作压根不该派给本素材时（纯后端谈首屏、纯代码谈字幕、在后端仓库查字体授权），才用 `not_applicable`。
>
> | 情形 | 正确归类 | 理由 |
> |---|---|---|
> | 去找 X，**X 不存在** | **🟢 实测发现** | 你**确实执行了**这个动作，只是结果是"没有"。留在分母内，计 green |
> | 该动作属于**本素材并不具备的类型** | `not_applicable` | 如纯后端仓库谈"首屏"——这类型压根不该被派下来 |
> | 角色签名动作**超出本素材领域** | `not_applicable` | 如版权律师在纯后端仓库查字体授权 |
>
> **为什么把这一格划这么细**：把"没有测试"归成"不适用"，会同时造成两件坏事 —— 最高价值的发现被归档成"未执行"（报告里根本看不见），同时还从尽责率分母里扣掉（分数反而更好看）。**发现丢失 + 分数虚高，而且不需要任何坏意图。**
>
> **顺带一提**：在这个定义下，"真去看一眼"比"声称不适用"**更省事且得分更高**——一条 `ls` 或 `grep` 就能换一个 🟢。诚实在这里就是最优解，不必靠人盯着。

- 你本来就要写 `why`，只是多勾一个枚举，**零额外思考成本**。
- 这个字段的价值在于：让脚本**不用猜**一条 🔴 到底是环境问题还是模型偷懒 —— 猜是猜不准的，必须在产生端标注。
- **反滥用（别踩）**：`cause=env_missing` 但该工具在 `EnvProbe` 中显示**可用** → 触发违规码 `FALSE_ENV_EXCUSE`，该条被**强制改判为 `budget_exhausted`** 并计入分母重算尽责率。拿环境当挡箭牌只会让尽责率更难看。
- 同理，真的预算耗尽就老实写 `budget_exhausted`，别伪报成 `env_missing`。

### 5.3 覆盖度 `coverage`

```
coverage = A_done / A_planned      （写成分数形式，如 26/32，不转百分比）
```

- `A_planned` = Σ 各角色 Brief 中 `key_actions` 条数 + `signature_actions` 条数 + `3`（DXP 步 3 强制的最少边缘尝试）。该值由 BriefBuilder 在派发时写入 `meta.json` 的 `casting[].planned_actions`，**verify 脚本只读不算**。
- `A_done` = Σ 各角色 `step2_main_path[]` + `step3_edge_attempts[]` 中 `evidence.level ∈ {green, yellow}` 的条目数。
- 分子可以大于计划（角色多做了），此时**如实呈现**，不裁剪。

### 5.4 降级原因清单 `degradation_reasons`

- 每条结构：`{what, why, cause, how_user_can_verify}`，`cause` 为 §5.2.1 四值之一，**必填**。
- 汇总全部角色的 `degradation_reasons[]`，**先按 `cause` 分组**，组内按 `why` 语义去重合并，保留每条的 `how_user_can_verify`。
- 环境层面的强制降级（`EnvProbe.forced_red_scopes`，如本机无 ffmpeg）单独成条，`cause=env_missing`，并附 `install_hints` 中的安装命令原文。
- 全部登记进报告末版《更正与声明》，**按 `cause` 分组呈现**，环境类单列。
