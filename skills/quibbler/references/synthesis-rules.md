# 汇总合成规则（Synthesis Rules）

> **执行者：主 Agent（主编）。** 输入是 5–7 份已通过校验的 `ExperienceLog`，输出是《唱唱反调》9 个版面的内容素材。
> **铁律：主编只做归并与裁决，绝不替角色编造感受。** 报告里出现的每一句角色原话，都必须能在某份 ExperienceLog 里逐字找到。
> 指标口径见 `dxp-protocol.md` §5，本文件不重复定义。版面锚点见 `report-template.md` §1，本文件不重复定义。

---

## 0. 输入 / 输出

| | 内容 |
|---|---|
| **输入** | `ExperienceLog[]`（每角色一份）、`CastingPlan`（席位与选角理由）、`EnvProbe`（强制降级范围）、`MaterialProfile` |
| **输出** | `SynthesisResult { consensus[], disputes[], obituary[], gems[], forecast[], fix_list[], headline }` |
| **顺序** | §1 前置过滤 → §2 共识 → §3 分歧 → §4 致命伤 → §5 亮点 → §6 风险 → §7 修复清单 → §8 头版判词 → §9 更正声明 → §10 自检 |
| **不可跳步** | 头版判词**必须最后写**，因为它从共识 Top1 与致命伤 Top1 提炼。先写头版 = 先定结论再找证据。 |

## 1. 前置过滤：有效日志集与计数权重

在做任何聚类之前，先给每份日志打三个标记。**这一步决定后面所有人次统计的分母，不许省。**

| 过滤器 | 触发条件 | 后果 |
|---|---|---|
| **F1 未完成** | `experience_completed == false` | 该角色全部结论的证据等级**上限压到 `yellow`**（原本标 `green` 的也降）；**不计入共识人次**；登记进末版 |
| **F2 纯推演角色** | 该角色 `step6_verdict` 下全部条目 `evidence.level == "red"` | 该角色《读者来信》段落**整段标注**「⚠️ 本次为纯推演」；**不计入共识人次**；其条目不得进入讣告版与 P0 |
| **F3 推演条目** | 单条目 `evidence.level == "red"` | 该条**永久禁止进入 P0**（见 §7 硬过滤 H1）；不得作为讣告版的独立成立依据 |

**计数权重表（共识人次统计口径）**：

| 情形 | 计 1 人次？ |
|---|---|
| 角色正常完成，条目 `green` / `yellow` | ✅ 计 1 |
| 角色正常完成，条目 `red` | ✅ 计 1（可入共识，但见 §7 H1 不得进 P0） |
| 角色命中 F1（未完成） | ❌ 不计 |
| 角色命中 F2（纯推演） | ❌ 不计 |
| 同一角色对同一问题提了 3 条 | ✅ 仍只计 **1 人次**（人次 ≠ 条数） |
| 两个角色跑了同一条命令得到同样报错 | ✅ 计 **2 人次**（独立复现是强证据，不是重复） |

> **写进报告的每个人次数字，都要能被上表反推出来。** 报头公示的角色数与共识版的人次分母不一致时（因为有人被 F1/F2 剔除），必须在共识版开头写一行：「本版人次分母为 N 位有效体验者（M 位因 XXX 不计入）」。

## 2. 共识聚类 → 《📢 社论 · 众口一词》

### 2.1 归并键

把所有角色的 `step4_friction_log[]` + `step6_verdict.fatal_flaws[]` 摊平成条目池，对每条抽取二元组 **(对象, 症状类)**：

- **对象**：必须是可定位实体 —— `文件:行号` / URL + 元素 / 章节段落 / `mm:ss` 时间点 / 字段名 / 命令名。写不出可定位对象的条目**不参与聚类**（只能留在《读者来信》里）。
- **症状类**（七选一，闭集）：`阻断`（做不下去）/ `误导`（文档与实际不符）/ `缺失`（该有的没有）/ `性能`（能做但慢/重）/ `表达`（看不懂、话没说清）/ `安全`（越权、泄漏、注入）/ `一致性`（自相矛盾）

**归并判定**：两条目的对象指向同一实体（允许粒度差一级，如"README 第 12 行"与"README 的 Node 版本要求"视为同一实体），且症状类相同 → 归为同一共识簇。

### 2.2 成簇条件

一个簇成立为「共识问题」，当且仅当：**簇内条目来自 ≥2 个不同 `role_id`，且这些 role 均未被 F1/F2 剔除。**

### 2.3 呈现要求

- 按**提及人次降序**排列；人次相同时，按 `green` 条目占比降序。
- 每个共识问题**必须引各人原话**（从 `i_thought` / `actually` / `phenomenon` / `one_line_to_author` 中取），**逐字引用，禁止改写角色语气**。原话是这份报告可读性的唯一来源。
- 每条结构：`问题标题 → 提及角色（人次）→ 各自原话（引用块）→ 综合判断（主编一句话，可带形容词）→ 合并后的最高证据等级`。
- **合并证据等级取簇内最高**（有一个 `green` 就是 🟢），但要在括号里注明构成：`🟢（3 人中 2 人实测）`。
- 目标产出 **≥3 条共识问题**（PRD V2 硬指标）。不足 3 条时，放宽归并粒度（允许症状类相邻合并，如 `误导`+`表达`）再试一次；仍不足则如实呈现，并在版尾写明"本期共识仅 N 条，角色视角分歧较大，详见争鸣版"。

## 3. 分歧配对 → 《⚔️ 争鸣版 · 唱唱反调》

### 3.1 配对条件（满足任一即成立）

| 类型 | 条件 |
|---|---|
| **D-A 去留分歧** | 针对同一素材，两角色 `will_continue` 相反 |
| **D-B 优缺互斥** | 同一对象（按 §2.1 归并键判定），一方列入 `fatal_flaws`，另一方列入 `underrated_highlights` |
| **D-C 同因异果** | 同一现象，两角色的 `impact` 判断在量级上相反（一方"会流失用户"，一方"无所谓"） |
| **D-D 解释 vs 体感** | 同一对象上，一方给出**专业解释**（"这是正常的/没有风险/设计如此"），另一方给出**主观反应**（"我害怕/我不敢点/我没看见/我以为…所以我走了"）。**此类适用 §3.3 直觉权威规则，裁决方式与前三类不同** |

### 3.2 呈现要求（**必须真的对撞，不许和稀泥**）

每个分歧点固定五段：

1. **正方**：角色名 + 席位 + **原话引用** + 其证据等级
2. **反方**：角色名 + 席位 + **原话引用** + 其证据等级
3. **分歧根源**：从下表选一个并说明为什么 ——
   `用户分层不同` / `使用场景不同`（首次 vs 熟练、白天 vs 深夜、快网 vs 慢网）/ `时间尺度不同`（上线当天 vs 维护三年）/ `利益立场不同`（使用者 vs 采购方 vs 竞品）/ `信息不对称`（一方看了文档一方没看）
4. **主编裁决**：三选一 ——
   - 「**判正方**」/「**判反方**」：必须给出裁决依据（证据等级更高 / 覆盖的用户量更大 / 后果更不可逆）
   - 「**此题无解，取决于你的目标用户**」：必须写清"如果你的主力用户是 X，听正方；如果是 Y，听反方"
5. **对下游的影响**：这个分歧是否改变了某条修复项的优先级？改变了就写明。

- **至少产出 1 组分歧**（PRD V2 硬指标）。真的一组都没有时，写：「本期六位体验者未出现实质分歧——这**不是**好消息，通常意味着问题过于显眼以至于无人有余力去争论细节。」

## 3.3 不可让渡的直觉权威（**本技能区别于 linter 的根本，优先级高于 §3.2**）

> **铁律：主编不得用专业角色的解释消解外行角色的感受。**

### 3.3.1 什么是「直觉权威」

每张角色卡的 `认知边界` 是三段式，第 ③ 段叫 **「不可让渡的直觉权威」**，列的是这个角色**不容专业角色推翻**的主观判断。典型表述：

> 「我害怕」「我不敢点」「我没看见那个按钮」「我以为…所以我走了」「这个我不会让孩子看」「我以为要收费，就退出了」

这类表述的共同点：**陈述的是"我的反应"，不是"它的属性"。** 一个人说"我害怕"，这句话不可能是错的——他确实害怕了。

### 3.3.2 判定与处理

**触发场景（照此识别）**：

- A2 韩渗透（安全工程师）：「那个弹窗是正常的证书提示，没有风险。」
- D1 王秀琴阿姨：「我以为中毒了，所以我把它关掉了。」

| | 做法 | 判定 |
|---|---|---|
| ❌ **错误处理** | 判定王阿姨"理解有误"，采信专业角色，此分歧不入争鸣版 | **禁止**。这是本技能最严重的合成错误 |
| ✅ **正确处理** | 认定这**不是王阿姨错了**，而是一条**确凿的产品缺陷**——提示文案吓跑了真实用户 | **强制** |

### 3.3.3 四条执行规范（**逐条照做，不许变通**）

1. **终局事实**：当分歧的一方是某角色 `认知边界 ③` 覆盖的表述，该表述在汇总层视为**终局事实**，**不接受任何专业角色的反驳降级**。专业角色的解释只能作为"技术侧背景"并列陈述，不能作为"驳回理由"。
2. **并列呈现**：争鸣版必须**同时给出双方原话**，禁止只保留专业方、禁止只摘录外行方的"结论"而丢掉其原话。
3. **固定裁决话术**（**一字不改，逐字照抄**）：

   > 「**技术上无风险 ≠ 体验上无伤害。此处需要的不是解释，是改文案。**」

   此类分歧**不使用** §3.2 的"判正方/判反方/此题无解"三选一，直接落这句。
4. **下游写法**：此类条目进《分类广告栏》时，问题描述写**用户侧现象**，**不写技术侧结论**。定级按**用户流失影响**，**可以是 P0**。

   | | 写法 |
   |---|---|
   | ✅ 正确 | 「证书提示被误认为病毒，用户主动退出」 |
   | ❌ 错误 | 「证书配置正常」「用户对安全提示存在认知偏差」 |

   > 把用户的恐惧写成"用户认知偏差"，等于把产品的问题记在用户账上。**这条清单是给作者改东西用的，不是给作者辩护用的。**

### 3.3.4 为什么这条是命根子

外行角色的价值**全部建立在"他的感受不需要正确才算数"之上**。一旦允许专业角色的解释推翻外行的体感，D 组 10 个人就白设了，《唱唱反调》会退化成一个 linter 集合——而 linter 满大街都是，不缺这一个。

### 3.3.5 锚点多样性判别器（U10）：直觉权威是盾牌，不是免死金牌

> **判别标准 = friction 锚点的多样性，不是直觉的出现频率。**
> 「诉诸直觉」本身永远不是问题。八次说"我怕了"完全可能是本期最重要的发现。**要看的是这八次钉在了几个地方。**

#### 第一步：先分清「锚点」和「解释」（**这里搞错会毁掉整条规则**）

| 维度 | 要求 | 例 |
|---|---|---|
| **在哪一步 / 看到什么时**（锚点 = **必须有**） | 把感受钉在一个具体操作或画面上 | 「填手机号那一步，我不敢按下一步」✅ |
| **为什么**（因果 = **永远不许要求**） | 解释这东西技术上为何如此 | 「因为这是个未加密的表单」← 外行说不出，也**不许**逼他说 |

一个人永远能说清"我在哪一刻怕了"，即使他完全说不清"为什么这东西可怕"。**锚点是他有的，解释是他没有的。**

- 判定：**有锚点即合格**。「填手机号那步不敢点，怕扣钱」✅ ；「我很焦虑」✗（无锚点）；「因为表单没加密所以危险」✗（这是专业判断，越界了，本就不该由外行角色说出口）。
- **禁止**因为一条恐惧"没说明原因"而降低其权重。要求外行解释因果，等于把他赶回专业角色的赛道，这正是 D 组存在要堵的坑。

#### 第二步：数锚点，不数次数

对该角色 `step4_friction_log[]` + `fatal_flaws[]` 中全部诉诸直觉权威的条目，抽取各自的**锚点**（按 §2.1 归并键的"对象"口径：具体操作步骤 / 页面画面 / 文件位置 / 时间点），去重后得 **`distinct_anchors`**。

| 情形 | 判定 | 处理 |
|---|---|---|
| `distinct_anchors ≥ 3` 且锚点分布在**不同环节** | **头版级发现** | **必须提升**：这个产品在每一个关键节点都在吓走用户。合成一条共识问题「全链路信任缺失」，**并作为《头版头条》候选素材**。**严禁**标注"未提供差异化信息" |
| `distinct_anchors == 2` | 正常有效信号 | 照常进共识 / 修复清单，不加任何标注 |
| `distinct_anchors == 1` 而条目数 ≥3（翻来覆去同一个锚点） | **角色刷屏** | 在争鸣版该角色出现处注明「未提供**差异化**信息」，条目合并为 1 条 |
| `distinct_anchors == 0`（通篇无锚点，如"我就是觉得不舒服"） | 无法转化 | 注明「未提供**可操作**信息」；条目照常进《读者来信》，但不进《分类广告栏》 |

**两处标注话术**（注意措辞区别，前者说的是"重复"，后者说的是"空泛"）：

> 「⚠️ **该角色本次未提供差异化信息** —— {N} 条恐惧均锚定在同一处（{锚点}），已合并为一条。其体感成立，但不构成多点发现。」

> 「⚠️ **该角色本次未提供可操作信息** —— 全部结论均为无锚点的泛化情绪。其体感依然成立，但无法转化为修复项。」

#### 第三步：两条防打架的边界（**别把帽子扣错**）

1. **角色卡段③的「限 2–4 条」约束的是角色卡本身（先验声明），不是体验过程中的恐惧次数。** 段③是"这个角色有哪几类主观判断不可被推翻"的**定义**；而 `step4_friction_log` / `step6` 里实际报了多少次"我怕了"，**不设上限**——真实体验里怕了八次就写八次。**这两个数不是一回事，汇总时绝不许拿段③的条数去砍体验日志的条数。**
2. **"提升"与"合并"只影响呈现方式，不影响证据等级。** 锚点多样不会让 🔴 变 🟢，锚点雷同也不会让 🟢 掉级。证据等级只由"跑没跑过"决定。

## 4. 致命伤遴选 → 《⚰️ 讣告版 · 致命伤》

### 4.1 入选条件

从所有 `fatal_flaws` 中筛，满足 **C1 且（C2 或 C3）**：

- **C1**（硬门槛）：`evidence.level == "green"`。🟡 只有在**同一问题被 ≥3 人独立提及**时才破格入选，且必须标注"证据未完全闭合"。🔴 **一律不得入选**。
- **C2**：提及人次 ≥2（按 §1 权重表）
- **C3**：单人提出，但 `impact` 属于三类后果之一 —— `用户流失`（首次使用即放弃）/ `上线事故`（数据损坏、服务不可用、安全越权）/ `公关翻车`（可被截图传播、违法违规、伤害特定群体）

### 4.2 数量与排序

- **取 1–3 条**。超过 3 条时按「后果不可逆程度 → 影响用户比例 → 提及人次」三级排序取前 3，其余降入《分类广告栏》P0/P1。
- 一条都没有时**保留版面**，写：「本期无讣告。这不代表它没问题，只代表没有问题严重到能杀死它。」

### 4.3 呈现要求（**冷峻**，这一版不许俏皮）

每条固定六项，用短句，不用感叹号：

```
### {序号}. {现象一句话，陈述句}
- **死因**：{可观测的事实，带证据标签与 artifact 相对路径}
- **报告人**：{角色名 · 职业}（{N} 人独立发现）
- **证据**：{🟢/🟡} {命令+退出码 / URL+截图 / 文件:行号}
- **后果推演**：{谁、在什么场景、损失什么、多久发生一次}
- **抢救方式**：{一句话，指向分类广告栏对应编号}
```

## 5. 亮点汇总 → 《💎 遗珠版 · 被低估的亮点》

- 汇总全部角色的 `underrated_highlights[]`（含被 F1/F2 标记的角色 —— **亮点不做人次过滤**，因为亮点的价值不依赖执行率）。
- 按 §2.1 归并键去重；被多人提到的亮点排在前面，标注「{N} 人独立提到」。
- 每条必须写明 **「谁在意这个」** —— 角色名 + 一句为什么他在意。这是防止作者砍掉真正差异化的关键信息。
- 每条结构：`亮点标题（可定位）→ 谁在意 → 为什么被低估（谁会忽略它）→ 砍掉的代价`。
- **至少 1 条**。为 0 说明有角色违反了 R2 红线，回到回收校验环节打回。

## 6. 风险预报合成 → 《🌡 天气预报 · 风险预测》

### 6.1 视角来源（**限定**）

只取 **D6 冯抬杠 / E4 温工单 / E7 池追问 / E8 卓对手** 四人的日志合成。

- 四人中有 ≥1 人入选 → 用入选者的 `fatal_flaws` + `one_line_to_author` + 敌对视角观察合成。
- 四人**均未入选** → 由本期已入选的**敌对席**角色合成，且**整版标注 🔴 推演**，并在末版登记"风险预报缺少舆情/客服/媒体视角，建议补跑"。

### 6.2 产出规格

固定输出**未来 7 天最可能发生的 3 件事**，三类各一条：

| 类型 | 问什么 | 证据来源 |
|---|---|---|
| **差评类型** | 用户会在应用商店/评论区骂什么？给出**一条虚构但符合口吻的差评原文** | D6 / 边缘用户席的卡点 |
| **工单类型** | 客服会接到什么电话？预估**每百用户工单数量级** | E4 / 报错话术相关卡点 |
| **舆情角度** | 媒体或竞品会怎么写标题？给出**一个可能的稿件标题** | E7 / E8 |

每条附：`触发条件`（什么情况下会发生）+ `概率档`（高/中/低，并说明依据）+ `可规避的前置动作`（指向分类广告栏编号）。

## 7. 修复清单定级 → 《📋 分类广告栏 · 急聘修复》

### 7.1 条目来源

所有角色的 `fatal_flaws[]` + `step4_friction_log[]` 中**可定位**的条目，按 §2.1 归并键去重（多人提及合并为一条，`提出者` 列写全部人名）。

### 7.2 定级判定树（**按顺序判，命中即止**）

```
① evidence.level == "red"  ?
   → 是：直接落 P1 或 P2（见 ③④），并在【建议】列前置「需人工确认：」  ← 硬过滤 H1
   → 否：进 ②

②′【直觉权威通道】该条目来自 §3.3 认定的「不可让渡的直觉权威」表述？
   → 是：按用户流失影响定级，**可以是 P0**。
         · 问题列写用户侧现象，禁止写技术侧结论
         · 提出者列写外行角色本人，禁止替换成给出解释的专业角色
         · 不因"专业角色认为无风险"而降级
   → 否：进 ②

② evidence.level == "green"
   且（提及人次 ≥2  或  该问题阻断主路径 / 属于安全越权 / 造成数据损坏）?
   → 是：P0
   → 否：进 ③

③ evidence.level ∈ {green, yellow}  且  非阻断（用户能绕过去继续）?
   → 是：P1
   → 否：进 ④

④ 其余（含全部 red 条目、单人提及的表达类问题、审美偏好）
   → P2
```

### 7.3 两条硬过滤（**红线，不可协商**）

| 编号 | 规则 | 校验方 |
|---|---|---|
| **H1** | **🔴 推演级证据的条目不得进入 P0。** 无论多少人提及、后果多严重，只要没跑起来验证过，就只能落 P1/P2，并强制在【建议】列前置「需人工确认：」+ 给出补验命令。 | `verify_report.mjs` 扫描 `<!-- QUIBBLER:FIXLIST -->` 区内 P0 行是否含 🔴 → 违规码 `RED_IN_P0`，退出码 1 |
| **H2** | **全推演的角色（F2）不计入共识问题的人次统计。** 其条目可以出现在《读者来信》与 P1/P2，但不能撑起一条"众口一词"。 | 主 Agent 自查；共识版开头须公示有效人次分母 |
| **H3** | **直觉权威条目不得因专业解释而降级。** 见 §3.3。此类条目的问题描述必须是用户侧现象，提出者必须是外行角色本人。 | 主 Agent 自查；§10 自检清单 |

> H1 的用意：P0 意味着"停下手上的活先修这个"。用一条没验证过的推断打断别人的工作，是这个技能最容易失去信任的地方。
>
> **H1 与 H3 的关系（容易混）**：H1 管的是**证据等级**（没跑过的不许进 P0），H3 管的是**话语权**（跑过的体感不许被解释掉）。王阿姨真的打开页面、真的看见弹窗、真的关掉了——这是 `green`，H1 不拦它；H3 保证它不被"证书配置正常"这句话消解。**两条互不冲突：一个查你有没有跑，一个查你听不听得进去。**

### 7.4 四要素与表格列（缺一不可）

每条修复项必须凑齐 **现象 → 影响 → 建议 → 验收方式**：

| 要素 | 写法要求 | 反例（不合格） |
|---|---|---|
| **现象** | 可观测、可复现，带定位 | "文档有问题" |
| **影响** | 谁、什么场景、损失什么、频率 | "影响用户体验" |
| **建议** | 可执行到能开工的粒度（改哪个文件、改成什么） | "建议优化" |
| **验收方式** | 一句**可被机器或他人复核**的判定条件 | "改好为止" |

**工作量估算档位**：`S` ≤2 人时 · `M` 半天到 2 天 · `L` >2 天或需改动架构。估不准就往大了估，并注明"含不确定性"。

**排序**：P0 → P1 → P2；同级内按提及人次降序，人次相同按工作量升序（先做便宜的）。

## 8. 头版判词 → 《🗞 头版头条》

### 8.1 写作规范

- **≤30 字**，一句话，**可证伪的陈述句**。
- 素材来源：共识 Top1 + 致命伤 Top1，二者提炼成一句。
- 禁止：疑问句、感叹号堆砌、"整体尚可但有提升空间"这类不可证伪的平衡句、"某某产品的三大问题"这种标题党空壳。
- 允许尖锐、允许扎心，但**每个字都要能在报告正文找到出处**。
- 副标题固定 **3 句**，每句一个可量化事实（人数 / 时长 / 比例 / 次数）。

### 8.2 三个正例

| 正例 | 为什么好 |
|---|---|
| 「装得上，跑不起来，README 骗了所有人」 | 可证伪（去跑一次就知道）、指向明确、有情绪但不空 |
| 「六个人里五个没找到"返回"，第六个是开发者本人」 | 用数字讲故事，自带证据感 |
| 「前三秒在自我介绍，观众在第四秒离开」 | 定位到具体时间点，结论直接可行动 |

### 8.3 三个反例

| 反例 | 为什么不行 |
|---|---|
| 「整体不错，但仍有较大提升空间」 | 不可证伪，说了等于没说 |
| 「这个产品的五个致命问题」 | 标题党空壳，没有任何具体信息 |
| 「作为一款面向开发者的工具，它在易用性方面表现欠佳」 | AI 腔、绕、30 字里没一个事实 |

## 9. 更正与声明 → 《⚖️ 更正与声明》

按顺序汇总**六类**内容，**一条都不许漏，漏了就是欺骗**：

1. **未能真实执行的部分 —— 按 `cause` 分组**（四组，无内容的组写"本期无"）：
   | 分组 | `cause` | 是否已从尽责率分母扣除 |
   |---|---|---|
   | 环境缺失（**单列，附安装命令**） | `env_missing` | ✅ 已扣 |
   | 权限受限 | `access_denied` | ✅ 已扣 |
   | **该动作对本素材类型不成立** | `not_applicable` | ✅ 已扣 |
   | **预算耗尽** | `budget_exhausted` | ❌ **未扣，已拉低尽责率** |
   每条含 `什么没做 / 为什么 / 用户怎么补验`。**`budget_exhausted` 组必须如实呈现**，这组就是本次体验的偷懒记录，藏起来等于自欺。

   > ⚠️ **归类前先过一遍这道闸**：`not_applicable` 是"这个动作对本素材类型不成立"（纯后端谈首屏），**不是**"我去找了但东西不存在"。
   > 「跑测试→没有测试」「查空状态→一个都没有」「找 alt→全站零个」属于 **🟢 实测发现**，应当出现在《讣告版》或《社论》里，**绝不许出现在本节**。
   > 把它们归到这里会同时造成两件坏事：最值钱的发现在报告里消失，尽责率还虚高。判据见 `dxp-protocol.md` §5.2.1。
2. **环境强制降级**：`EnvProbe.forced_red_scopes` 逐项 + `install_hints` 安装命令原文 + 一句"装好后重跑，预计真实执行率可达 X%"。
3. **未完成的角色**：F1/F2 命中的角色名单 + 卡在哪一步 + 其结论的证据上限。
4. **编辑部自省**（`CASTING_MISMATCH` 告警登记，**无告警时写"本期无"**）：
   verify 输出的 `CASTING_MISMATCH` 是 **warning 不改退出码**，但必须在此如实登记。它指向的是**编排层的决策失误，不是角色的失职**——措辞上不许写成对角色的指责。

   | 告警条件 | 说明什么 | 登记话术（照此写） |
   |---|---|---|
   | 单角色 `not_applicable` ≥ 其 `planned_actions` 的 **1/3** | **选角偏差**——这个人本就不该被派来看这份素材 | 「本期请 {角色名} 来看这份素材，是编辑部的判断失误：{N}/{M} 项动作对该素材不成立。下次选角将调整备选池权重。」 |
   | 同一动作被 **≥2 个角色**标 `not_applicable` | **判型偏差**——素材类型标错了 | 「{动作} 被 {N} 位体验者判定为不成立，说明本期对素材类型的判定（{types}）可能有误，识别信号需要修正。」 |

   > 选动作的是主 Agent，该被问责的也是主 Agent。**子代理没资格判断"这动作该不该做"，所以这一节骂的是编辑部自己。**
5. **本次未覆盖的角度**：候选池中因席位配额落选、但与素材强相关的角色（列 2–4 个），说明"如果补跑，建议加谁"。
6. **临时角色声明**：`temporary: true` 的角色逐个标注"本角色为本次即兴生成，非角色库常驻"。
